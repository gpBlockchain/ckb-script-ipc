# CIP-0002: Standard Crypto Service Interface

| CIP | 0002 |
|-----|------|
| Title | Standard Crypto Service Interface |
| Author | CKB Script IPC Team |
| Status | Draft |
| Type | Standards Track |
| Category | Interface |
| Created | 2026-02-06 |
| Requires | CIP-0001 |

## Abstract

This CIP defines a standard interface for cryptographic services in CKB scripts via IPC. It specifies a common set of cryptographic operations including hash functions, digital signature verification, and public key recovery that can be shared across multiple CKB scripts through a service-client architecture.

## Motivation

Cryptographic operations are fundamental to blockchain scripts but often require significant code size and computational resources. By defining a standard crypto service interface:

1. **Code Reuse**: Scripts can share a single crypto service implementation, reducing overall on-chain code size
2. **Interoperability**: Different scripts can communicate using a common crypto interface
3. **Upgradability**: Crypto implementations can be upgraded without modifying dependent scripts
4. **Security**: A well-audited, shared crypto service reduces the attack surface compared to multiple independent implementations

## Specification

### Service Trait Definition

The crypto service MUST be defined using the `ckb_script_ipc::service` macro:

```rust
#[ckb_script_ipc::service]
pub trait CkbCrypto {
    // Hash functions
    fn hasher_new(hash_type: HasherType) -> HasherCtx;
    fn hasher_update(ctx: HasherCtx, data: Vec<u8>) -> Result<(), CryptoError>;
    fn hasher_finalize(ctx: HasherCtx) -> Result<Vec<u8>, CryptoError>;

    // Signature operations
    fn secp256k1_recovery(
        prehash: Vec<u8>,
        signature: Vec<u8>,
        recovery_id: u8,
    ) -> Result<Vec<u8>, CryptoError>;

    fn secp256k1_verify(
        public_key: Vec<u8>,
        prehash: Vec<u8>,
        signature: Vec<u8>,
    ) -> Result<(), CryptoError>;

    fn schnorr_verify(
        public_key: Vec<u8>,
        prehash: Vec<u8>,
        signature: Vec<u8>,
    ) -> Result<(), CryptoError>;

    fn ed25519_verify(
        public_key: Vec<u8>,
        prehash: Vec<u8>,
        signature: Vec<u8>,
    ) -> Result<(), CryptoError>;
}
```

### Data Types

#### HasherType Enumeration

Specifies the hash algorithm to use:

```rust
#[derive(Serialize, Deserialize)]
pub enum HasherType {
    CkbBlake2b,   // CKB-specific Blake2b with personalization
    Blake2b,      // Standard Blake2b-256
    Sha256,       // SHA-256
    Ripemd160,    // RIPEMD-160
}
```

| Variant | Output Size | Description |
|---------|-------------|-------------|
| `CkbBlake2b` | 32 bytes | Blake2b with CKB personalization ("ckb-default-hash") |
| `Blake2b` | 32 bytes | Standard Blake2b-256 |
| `Sha256` | 32 bytes | SHA-256 |
| `Ripemd160` | 20 bytes | RIPEMD-160 |

#### HasherCtx

An opaque context handle for streaming hash operations:

```rust
#[derive(Clone, Serialize, Deserialize)]
pub struct HasherCtx(pub u64);
```

The context ID is managed by the server and MUST be unique per active hasher instance.

#### CryptoError

Error types that can be returned by crypto operations:

```rust
#[derive(Debug, Serialize, Deserialize)]
pub enum CryptoError {
    InvalidContext,    // The hasher context is invalid or expired
    InvalidSig,        // Signature format is invalid
    InvalidPrehash,    // Prehash length is incorrect
    InvalidRecoveryId, // Recovery ID is out of valid range
    InvalidPubkey,     // Public key format is invalid
    RecoveryFailed,    // Public key recovery failed
    VerifyFailed,      // Signature verification failed
}
```

### Method Specifications

#### Hash Operations

##### `hasher_new(hash_type: HasherType) -> HasherCtx`

Creates a new hasher context for the specified algorithm.

- **Parameters**: 
  - `hash_type`: The hash algorithm to use
- **Returns**: A hasher context handle
- **Errors**: Never fails

##### `hasher_update(ctx: HasherCtx, data: Vec<u8>) -> Result<(), CryptoError>`

Updates the hasher with additional data.

- **Parameters**:
  - `ctx`: The hasher context
  - `data`: Data to hash
- **Returns**: `Ok(())` on success
- **Errors**: `InvalidContext` if the context is invalid

##### `hasher_finalize(ctx: HasherCtx) -> Result<Vec<u8>, CryptoError>`

Finalizes the hash computation and returns the digest. The context is invalidated after this call.

- **Parameters**:
  - `ctx`: The hasher context
- **Returns**: The hash digest
- **Errors**: `InvalidContext` if the context is invalid

#### Signature Operations

##### `secp256k1_recovery(prehash: Vec<u8>, signature: Vec<u8>, recovery_id: u8) -> Result<Vec<u8>, CryptoError>`

Recovers a secp256k1 public key from a signature.

- **Parameters**:
  - `prehash`: 32-byte message hash
  - `signature`: 64-byte compact signature (r || s)
  - `recovery_id`: Recovery ID (0-3)
- **Returns**: 65-byte uncompressed public key (04 || x || y)
- **Errors**:
  - `InvalidPrehash`: prehash is not 32 bytes
  - `InvalidSig`: signature is not 64 bytes
  - `InvalidRecoveryId`: recovery_id > 3
  - `RecoveryFailed`: recovery computation failed

##### `secp256k1_verify(public_key: Vec<u8>, prehash: Vec<u8>, signature: Vec<u8>) -> Result<(), CryptoError>`

Verifies a secp256k1 ECDSA signature.

- **Parameters**:
  - `public_key`: 33-byte compressed or 65-byte uncompressed public key
  - `prehash`: 32-byte message hash
  - `signature`: 64-byte compact signature (r || s)
- **Returns**: `Ok(())` if signature is valid
- **Errors**:
  - `InvalidPubkey`: invalid public key format
  - `InvalidPrehash`: prehash is not 32 bytes
  - `InvalidSig`: signature is not 64 bytes
  - `VerifyFailed`: signature verification failed

##### `schnorr_verify(public_key: Vec<u8>, prehash: Vec<u8>, signature: Vec<u8>) -> Result<(), CryptoError>`

Verifies a Schnorr signature (BIP-340 compatible).

- **Parameters**:
  - `public_key`: 32-byte x-only public key
  - `prehash`: 32-byte message hash
  - `signature`: 64-byte Schnorr signature
- **Returns**: `Ok(())` if signature is valid
- **Errors**:
  - `InvalidPubkey`: public key is not 32 bytes
  - `InvalidPrehash`: prehash is not 32 bytes
  - `InvalidSig`: signature is not 64 bytes
  - `VerifyFailed`: signature verification failed

##### `ed25519_verify(public_key: Vec<u8>, prehash: Vec<u8>, signature: Vec<u8>) -> Result<(), CryptoError>`

Verifies an Ed25519 signature.

- **Parameters**:
  - `public_key`: 32-byte Ed25519 public key
  - `prehash`: 32-byte message hash
  - `signature`: 64-byte Ed25519 signature
- **Returns**: `Ok(())` if signature is valid
- **Errors**:
  - `InvalidPubkey`: public key is not 32 bytes
  - `InvalidPrehash`: prehash is not 32 bytes
  - `InvalidSig`: signature is not 64 bytes
  - `VerifyFailed`: signature verification failed

### Wire Format

All messages follow the CKB Script IPC wire format (see README.md):

**Request Packet:**
```
[version: VLQ] [method_id: VLQ] [length: VLQ] [payload: JSON]
```

**Response Packet:**
```
[version: VLQ] [error_code: VLQ] [length: VLQ] [payload: JSON]
```

Method IDs are assigned automatically by the service macro based on method order:

| Method | Method ID |
|--------|-----------|
| `hasher_new` | 0 |
| `hasher_update` | 1 |
| `hasher_finalize` | 2 |
| `secp256k1_recovery` | 3 |
| `secp256k1_verify` | 4 |
| `schnorr_verify` | 5 |
| `ed25519_verify` | 6 |

## Rationale

### Why Streaming Hash Interface?

The streaming hash interface (`hasher_new` → `hasher_update` → `hasher_finalize`) was chosen over a single `hash(data)` function for several reasons:

1. **Memory Efficiency**: Large inputs can be processed in chunks without loading entire data into memory
2. **Flexibility**: Allows hashing data from multiple sources incrementally
3. **CKB Compatibility**: Aligns with how hash functions are typically used in CKB scripts

### Why Separate Verification Methods?

Each signature scheme has distinct parameters and security properties. Separate methods:

1. Provide type safety at the interface level
2. Allow clear documentation of expected formats
3. Enable scheme-specific error handling

### Why Return `Vec<u8>` Instead of Fixed Arrays?

Using `Vec<u8>` for variable-length cryptographic data:

1. Simplifies serialization with serde
2. Avoids generic const parameters that complicate the macro system
3. Length validation is performed in the implementation

## Backwards Compatibility

This is a new interface standard. There are no backwards compatibility concerns.

Future versions of this interface should:
- Only add new methods, not modify existing ones
- Use new method IDs for new functionality
- Maintain wire format compatibility

### Usage Example

```rust
use ckb_crypto_interface::{CkbCrypto, CkbCryptoClient, HasherType};
use ckb_script_ipc_common::spawn::spawn_server;

// Start the crypto service
let (read_pipe, write_pipe) = spawn_server(0, Source::CellDep, &[])?;

// Create client
let mut client = CkbCryptoClient::new(read_pipe, write_pipe);

// Hash data using streaming interface
let ctx = client.hasher_new(HasherType::CkbBlake2b)?;
client.hasher_update(ctx.clone(), b"hello".to_vec())?;
client.hasher_update(ctx.clone(), b" world".to_vec())?;
let hash = client.hasher_finalize(ctx)?;

// Verify a secp256k1 signature
client.secp256k1_verify(pubkey, prehash, signature)?;
```

## Security Considerations

### Context Management

The hasher context IDs must be managed securely by the server:
- Context IDs should not be predictable
- Expired contexts must be invalidated to prevent reuse
- The server should limit the number of active contexts to prevent resource exhaustion

### Input Validation

All implementations MUST validate:
- Input lengths match expected sizes for cryptographic parameters
- Public keys are valid curve points
- Signatures are properly formatted

### Side Channel Attacks

Implementations SHOULD use constant-time operations where applicable to prevent timing attacks, especially in signature verification.

### Error Information Leakage

Error messages should not reveal sensitive information about the cryptographic operations or internal state.
