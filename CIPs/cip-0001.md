## What is a CIP?

CIP stands for CKB Script IPC Proposal. A CIP is a design document providing information to the CKB Script IPC community, describing a new feature, interface standard, or process for CKB script inter-process communication. The CIP should provide a concise technical specification of the feature and a rationale for it.

CIPs are inspired by [Ethereum's EIP process](https://eips.ethereum.org/EIPS/eip-1) and adapted for the specific needs of CKB script IPC development.

## CIP Rationale

We intend CIPs to be the primary mechanism for:

1. Proposing new IPC service interface standards
2. Defining communication protocols and wire formats
3. Documenting best practices for CKB script IPC development
4. Tracking the progress of implementations

## CIP Types

There are three types of CIPs:

### Standards Track CIP

Describes any change that affects CKB Script IPC implementations, such as:

- **Interface**: Standard service interfaces that can be implemented across different scripts (e.g., crypto services, storage services)
- **Protocol**: Changes to the wire format, packet structure, or communication protocol
- **Implementation**: Guidelines for implementing IPC clients and servers

### Meta CIP

Describes a process surrounding CKB Script IPC or proposes a change to a process. Examples include:

- Procedures and guidelines
- Changes to the decision-making process
- Changes to the CIP process itself

### Informational CIP

Describes a CKB Script IPC design issue or provides general guidelines or information to the community but does not propose a new feature.

## CIP Status Terms

- **Draft**: The initial state of a CIP while it is being refined
- **Review**: CIP is ready for peer review
- **Final**: CIP has been accepted and is considered complete
- **Active**: For CIPs that are continuously updated (like this one)
- **Withdrawn**: CIP has been withdrawn by the author(s)
- **Superseded**: CIP has been replaced by a newer CIP

## CIP Format

Each CIP should have the following parts:

### Preamble

A table containing metadata about the CIP:

| Field | Description |
|-------|-------------|
| CIP | The CIP number |
| Title | A short descriptive title |
| Author | Name(s) of author(s) |
| Status | Current status |
| Type | CIP type (Standards Track/Meta/Informational) |
| Category | For Standards Track: Interface/Protocol/Implementation |
| Created | Date created |
| Requires | CIP numbers this CIP depends on (optional) |
| Supersedes | CIP number this CIP supersedes (optional) |

### Abstract

A short (~200 word) description of the technical issue being addressed.

### Motivation

The motivation is critical for CIPs that want to change or add interfaces. It should clearly explain why the existing protocol or interface is inadequate.

### Specification

The technical specification should describe the syntax and semantics of any new feature. The specification should be detailed enough to allow competing implementations.

### Rationale

The rationale fleshes out the specification by describing what motivated the design and why particular design decisions were made.

### Backwards Compatibility

All CIPs that introduce backwards incompatibilities must include a section describing these incompatibilities and their severity.

### Reference Implementation

An optional section that contains a reference/example implementation.

### Security Considerations

All CIPs must contain a section that discusses security implications.

## CIP Workflow

### 1. Idea Stage

Before writing a CIP, discuss the idea with the community to gauge interest and get feedback.

### 2. Draft Stage

Write the CIP following this template and submit a pull request to the CIPs directory.

### 3. Review Stage

Once submitted, the CIP will be reviewed by maintainers and the community.

### 4. Final Stage

After sufficient review and any necessary revisions, the CIP can be marked as Final.

## File Naming Convention

CIP files should be named `cip-XXXX.md` where XXXX is the CIP number, padded with leading zeros (e.g., `cip-0001.md`, `cip-0023.md`).

## Auxiliary Files

CIPs may include auxiliary files such as diagrams or code samples. These should be placed in a subdirectory named `cip-XXXX/` (e.g., `cip-0002/interface.rs`).

## CIP Numbers

CIP numbers are assigned by the CIP editors. When submitting a new CIP, use `cip-draft-title.md` as the filename until a number is assigned.

### Reserved CIP Numbers

| Range | Purpose |
|-------|---------|
| 0001-0099 | Meta and process CIPs |
| 0100-0999 | Core protocol and interface standards |
| 1000-1999 | Crypto service interfaces |
| 2000-2999 | Storage and data service interfaces |
| 3000-3999 | Reserved for future use |
