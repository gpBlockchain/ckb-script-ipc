# CIP-0100: Standard Token Service Interface

| CIP | 0100 |
|-----|------|
| Title | Standard Token Service Interface |
| Author | CKB Script IPC Team |
| Status | Draft |
| Type | Standards Track |
| Category | Interface |
| Created | 2026-02-06 |
| Requires | CIP-0001 |

## Abstract

This CIP defines a standard interface for fungible token services in CKB scripts via IPC. Inspired by Ethereum's ERC-20 standard, it specifies a common set of token operations including balance queries, transfers, and allowance management that enables interoperable token implementations across CKB scripts through a service-client architecture.

## Motivation

Fungible tokens are a fundamental building block in blockchain ecosystems. A standardized token interface enables:

1. **Interoperability**: Different scripts and applications can interact with any compliant token using the same interface
2. **Ecosystem Growth**: Wallets, exchanges, and dApps can support all compliant tokens without custom integrations
3. **Code Reuse**: Common token logic can be shared across multiple token implementations
4. **Composability**: Tokens can be easily integrated into DeFi protocols, governance systems, and other applications

By adapting the widely-adopted ERC-20 pattern to CKB's IPC model, we leverage existing developer familiarity while optimizing for CKB's unique architecture.

## Specification

### Service Trait Definition

The token service MUST be defined using the `ckb_script_ipc::service` macro:

```rust
#[ckb_script_ipc::service]
pub trait CkbToken {
    // Token metadata
    fn name() -> String;
    fn symbol() -> String;
    fn decimals() -> u8;
    fn total_supply() -> U256;
    
    // Balance operations
    fn balance_of(owner: Address) -> U256;
    
    // Transfer operations
    fn transfer(to: Address, amount: U256) -> Result<bool, TokenError>;
    fn transfer_from(from: Address, to: Address, amount: U256) -> Result<bool, TokenError>;
    
    // Allowance operations
    fn allowance(owner: Address, spender: Address) -> U256;
    fn approve(spender: Address, amount: U256) -> Result<bool, TokenError>;
    
    // Extended operations (optional but recommended)
    fn increase_allowance(spender: Address, added_value: U256) -> Result<bool, TokenError>;
    fn decrease_allowance(spender: Address, subtracted_value: U256) -> Result<bool, TokenError>;
}
```

### Data Types

#### Address

Represents a CKB address (script hash):

```rust
#[derive(Clone, Debug, PartialEq, Eq, Serialize, Deserialize)]
pub struct Address(pub [u8; 32]);

impl Address {
    pub fn from_script_hash(hash: [u8; 32]) -> Self {
        Address(hash)
    }
    
    pub fn as_bytes(&self) -> &[u8; 32] {
        &self.0
    }
}
```

#### U256

A 256-bit unsigned integer for token amounts:

```rust
#[derive(Clone, Debug, PartialEq, Eq, Serialize, Deserialize, Default)]
pub struct U256(pub [u64; 4]); // Little-endian representation

impl U256 {
    pub const ZERO: U256 = U256([0, 0, 0, 0]);
    pub const MAX: U256 = U256([u64::MAX, u64::MAX, u64::MAX, u64::MAX]);
    
    pub fn from_u128(value: u128) -> Self {
        U256([value as u64, (value >> 64) as u64, 0, 0])
    }
    
    /// Adds two U256 values, returning None if overflow occurs.
    /// Implementations MUST return None instead of panicking or wrapping.
    pub fn checked_add(&self, other: &U256) -> Option<U256>;
    
    /// Subtracts other from self, returning None if underflow occurs.
    /// Implementations MUST return None instead of panicking or wrapping.
    pub fn checked_sub(&self, other: &U256) -> Option<U256>;
    
    /// Multiplies two U256 values, returning None if overflow occurs.
    /// Implementations MUST return None instead of panicking or wrapping.
    pub fn checked_mul(&self, other: &U256) -> Option<U256>;
}
```

#### TokenError

Error types that can be returned by token operations:

```rust
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub enum TokenError {
    /// Insufficient balance for transfer
    InsufficientBalance,
    /// Insufficient allowance for transfer_from
    InsufficientAllowance,
    /// Arithmetic overflow in calculations
    Overflow,
    /// Arithmetic underflow in calculations
    Underflow,
    /// Invalid address (zero address or malformed)
    InvalidAddress,
    /// Transfer to zero address
    TransferToZeroAddress,
    /// Approve to zero address
    ApproveToZeroAddress,
    /// Operation not permitted
    NotPermitted,
    /// Internal error
    InternalError,
}
```

### Method Specifications

#### Metadata Operations

##### `name() -> String`

Returns the name of the token.

- **Parameters**: None
- **Returns**: The token name (e.g., "CKB Token")
- **Errors**: Never fails

##### `symbol() -> String`

Returns the symbol of the token.

- **Parameters**: None
- **Returns**: The token symbol (e.g., "CKB")
- **Errors**: Never fails

##### `decimals() -> u8`

Returns the number of decimals used for display purposes.

- **Parameters**: None
- **Returns**: The number of decimals (typically 8 or 18)
- **Errors**: Never fails

##### `total_supply() -> U256`

Returns the total token supply.

- **Parameters**: None
- **Returns**: The total supply of tokens
- **Errors**: Never fails

#### Balance Operations

##### `balance_of(owner: Address) -> U256`

Returns the token balance of an address.

- **Parameters**:
  - `owner`: The address to query
- **Returns**: The token balance
- **Errors**: Never fails (returns 0 for unknown addresses)

#### Transfer Operations

##### `transfer(to: Address, amount: U256) -> Result<bool, TokenError>`

Transfers tokens from the caller to a recipient.

- **Parameters**:
  - `to`: The recipient address
  - `amount`: The amount to transfer
- **Returns**: `Ok(true)` on success
- **Errors**:
  - `InsufficientBalance`: Caller has insufficient balance
  - `TransferToZeroAddress`: Attempting to transfer to zero address
  - `Overflow`: Would cause balance overflow at recipient

**Events**: Implementations SHOULD emit a `Transfer` event on success.

##### `transfer_from(from: Address, to: Address, amount: U256) -> Result<bool, TokenError>`

Transfers tokens from one address to another using the allowance mechanism.

- **Parameters**:
  - `from`: The sender address
  - `to`: The recipient address
  - `amount`: The amount to transfer
- **Returns**: `Ok(true)` on success
- **Errors**:
  - `InsufficientBalance`: Sender has insufficient balance
  - `InsufficientAllowance`: Caller has insufficient allowance
  - `TransferToZeroAddress`: Attempting to transfer to zero address
  - `Overflow`: Would cause balance overflow at recipient

**Events**: Implementations SHOULD emit a `Transfer` event on success.

#### Allowance Operations

##### `allowance(owner: Address, spender: Address) -> U256`

Returns the remaining allowance that a spender is allowed to spend on behalf of the owner.

- **Parameters**:
  - `owner`: The token owner address
  - `spender`: The spender address
- **Returns**: The remaining allowance
- **Errors**: Never fails (returns 0 for no allowance)

##### `approve(spender: Address, amount: U256) -> Result<bool, TokenError>`

Sets the allowance for a spender to spend tokens on behalf of the caller.

- **Parameters**:
  - `spender`: The spender address
  - `amount`: The allowance amount
- **Returns**: `Ok(true)` on success
- **Errors**:
  - `ApproveToZeroAddress`: Attempting to approve zero address

**Security Warning - Approve Race Condition**: Setting allowance to a new value when the current allowance is non-zero carries a well-known race condition risk. A malicious spender can front-run the approval transaction to spend both the old and new allowances. 

**Recommended Mitigations**:
1. **Preferred**: Use `increase_allowance`/`decrease_allowance` which are atomic operations
2. **Alternative**: Set allowance to 0 first, wait for confirmation, then set to the new value (requires two transactions and is still vulnerable between transactions)
3. **Advanced**: Implement a `safe_approve(spender, expected_current, new_value)` that fails if current allowance doesn't match expected

**Events**: Implementations SHOULD emit an `Approval` event on success.

##### `increase_allowance(spender: Address, added_value: U256) -> Result<bool, TokenError>`

Atomically increases the allowance granted to a spender.

- **Parameters**:
  - `spender`: The spender address
  - `added_value`: The amount to add to allowance
- **Returns**: `Ok(true)` on success
- **Errors**:
  - `ApproveToZeroAddress`: Attempting to approve zero address
  - `Overflow`: Would cause allowance overflow

##### `decrease_allowance(spender: Address, subtracted_value: U256) -> Result<bool, TokenError>`

Atomically decreases the allowance granted to a spender.

- **Parameters**:
  - `spender`: The spender address
  - `subtracted_value`: The amount to subtract from allowance
- **Returns**: `Ok(true)` on success
- **Errors**:
  - `ApproveToZeroAddress`: Attempting to approve zero address
  - `Underflow`: Would cause allowance underflow

### Events

Token implementations SHOULD support event emission for off-chain indexing. Events are encoded in the response payload:

#### Transfer Event

Emitted when tokens are transferred.

```rust
#[derive(Serialize, Deserialize)]
pub struct TransferEvent {
    pub from: Address,
    pub to: Address,
    pub amount: U256,
}
```

#### Approval Event

Emitted when an allowance is set.

```rust
#[derive(Serialize, Deserialize)]
pub struct ApprovalEvent {
    pub owner: Address,
    pub spender: Address,
    pub amount: U256,
}
```

### Wire Format

All messages follow the CKB Script IPC wire format (see README.md):

**Request Packet:**
```
[version: VLQ] [method_id: VLQ] [length: VLQ] [payload: JSON]
```

**Response Packet:**
```
[version: VLQ] [error_code: VLQ] [length: VLQ] [payload: JSON]
```

Method IDs are assigned automatically by the service macro based on method order:

| Method | Method ID |
|--------|-----------|
| `name` | 0 |
| `symbol` | 1 |
| `decimals` | 2 |
| `total_supply` | 3 |
| `balance_of` | 4 |
| `transfer` | 5 |
| `transfer_from` | 6 |
| `allowance` | 7 |
| `approve` | 8 |
| `increase_allowance` | 9 |
| `decrease_allowance` | 10 |

## Rationale

### Why Follow ERC-20?

ERC-20 is the most widely adopted token standard in the blockchain ecosystem:

1. **Developer Familiarity**: Most blockchain developers know ERC-20
2. **Proven Design**: Battle-tested over years of production use
3. **Tooling Support**: Existing tools can be adapted more easily
4. **Documentation**: Extensive resources available

### Why U256 Instead of u128?

While CKB typically uses smaller integers, U256 provides:

1. **Compatibility**: Matches Ethereum's uint256 for easier porting
2. **Future-Proofing**: Supports tokens with very large supplies
3. **Precision**: Allows for tokens with many decimal places

### Why Separate increase_allowance/decrease_allowance?

These methods address the well-known ERC-20 approve race condition:

1. **Atomic Operations**: Prevent front-running attacks
2. **Safer Updates**: No need to check current allowance first
3. **Better UX**: Clearer intent in transactions

### Caller Identification

In CKB's IPC model, the caller's identity is determined by the script context, not an explicit `msg.sender`. Implementations MUST securely determine the caller's address from the transaction context.

## Backwards Compatibility

This is a new interface standard. There are no backwards compatibility concerns.

Future versions of this interface should:
- Only add new methods, not modify existing ones
- Use new method IDs for new functionality
- Maintain wire format compatibility

### Usage Example

```rust
use ckb_token_interface::{CkbToken, CkbTokenClient, Address, U256, TokenError};
use ckb_script_ipc_common::spawn::spawn_server;

// Start the token service
let (read_pipe, write_pipe) = spawn_server(0, Source::CellDep, &[])?;

// Create client
let mut client = CkbTokenClient::new(read_pipe, write_pipe);

// Query token metadata
let name = client.name()?;
let symbol = client.symbol()?;
let decimals = client.decimals()?;
let total_supply = client.total_supply()?;

println!("Token: {} ({}) with {} decimals", name, symbol, decimals);
println!("Total Supply: {:?}", total_supply);

// Check balance
let my_address = Address::from_script_hash(my_script_hash);
let balance = client.balance_of(my_address.clone())?;
println!("My balance: {:?}", balance);

// Transfer tokens
let recipient = Address::from_script_hash(recipient_script_hash);
let amount = U256::from_u128(1000_00000000); // 1000 tokens with 8 decimals
client.transfer(recipient.clone(), amount)?;

// Approve spender
let spender = Address::from_script_hash(spender_script_hash);
let allowance_amount = U256::from_u128(500_00000000);
client.approve(spender.clone(), allowance_amount)?;

// Check allowance
let allowance = client.allowance(my_address.clone(), spender.clone())?;
println!("Allowance for spender: {:?}", allowance);

// Transfer on behalf (requires allowance)
client.transfer_from(my_address, recipient, U256::from_u128(100_00000000))?;
```

## Security Considerations

### Reentrancy

Implementations MUST be protected against reentrancy attacks:
- State changes should occur before external calls
- Consider using reentrancy guards for complex operations

### Integer Overflow/Underflow

All arithmetic operations MUST check for overflow and underflow:
- Use checked arithmetic (`checked_add`, `checked_sub`, etc.)
- Return appropriate errors instead of panicking or wrapping

### Allowance Race Condition

The standard `approve` function has a known race condition:
- Users SHOULD use `increase_allowance`/`decrease_allowance` when possible
- If using `approve`, first set allowance to 0, then to the desired value
- Implementations MAY add a `safe_approve` that requires current allowance to be 0 or equal to expected value

### Address Validation

Implementations MUST validate addresses:
- Reject transfers to zero address
- Validate that addresses are properly formatted 32-byte script hashes

### Access Control

For token operations that require authorization:
- Verify caller identity from transaction context
- Implement proper access control for administrative functions (mint, burn, pause)

### Front-Running

Be aware of front-running risks in blockchain environments:
- Allowance changes can be front-run
- Large trades may be sandwich attacked
- Consider using commit-reveal schemes for sensitive operations

## Extensions

This standard can be extended with additional interfaces:

### Mintable Token

```rust
#[ckb_script_ipc::service]
pub trait CkbTokenMintable: CkbToken {
    fn mint(to: Address, amount: U256) -> Result<bool, TokenError>;
}
```

### Burnable Token

```rust
#[ckb_script_ipc::service]
pub trait CkbTokenBurnable: CkbToken {
    fn burn(amount: U256) -> Result<bool, TokenError>;
    fn burn_from(from: Address, amount: U256) -> Result<bool, TokenError>;
}
```

### Pausable Token

```rust
#[ckb_script_ipc::service]
pub trait CkbTokenPausable: CkbToken {
    fn paused() -> bool;
    fn pause() -> Result<(), TokenError>;
    fn unpause() -> Result<(), TokenError>;
}
```
